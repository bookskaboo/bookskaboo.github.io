# Quality assurance and playtesting

## Evidence baseline

Automated regression coverage exists for production, routing, research, world encounters, persistence, tutorials and UI helpers. Existing reports record passing checks at specific points; this plan does not convert those historical counts into a current test result.

The normal-play outpost run demonstrated Shiny, Complex delivery, Autonomous Logistics and remote Slag recovery. It did not complete Endgame Theory or the full robotics branches, establish sustainable Complex throughput, or exercise every random waste-recovery variant. Agent-based novice observations identify likely friction; they do not substitute for human participants.

Read [browser playtest startup and recovery](../browser-playtest.md) before starting or recovering a browser session. Preserve the current game. Use normal gameplay: no grants, save injection, accelerated simulation or changed rules. Queue ordinary bugs and design suggestions until the run ends. If progression is blocked, make only the smallest authorized fix, record it and continue.

Every exported run should retain seed, starting checkpoint, build identity when available, route/map roles, resource totals and elapsed game time. Separate setup and interaction overhead from production waiting. Record stockpiled inputs and outputs so temporary success is not mistaken for sustainable capacity.

## Issue record

Use a stable issue ID, affected build, reproduction steps, expected and actual behavior, severity, evidence and verification status. Distinguish a bug from a balance concern, a usability problem and a new feature request. Link related review questions without turning an undecided proposal into an implementation task.
