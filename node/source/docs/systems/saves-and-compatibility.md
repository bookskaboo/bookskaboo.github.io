# Saves and compatibility

[System index](README.md)

NODE stores game state locally in the browser. Three manual slots and an autosave retain the factory, world, research and applied mod. Undo uses a separate in-memory command history.

Audio settings are additive factory preferences: Music and Sound effects each retain a 0–100 volume and independent mute flag. Missing/invalid levels normalize to 50%; Undo keeps the current channel settings. The retired `sound` placeholder does not mute the new channels. Slots, autosaves, copies and exported/imported saves retain the settings, while practice reads the campaign's channel preferences. See [Audio](audio.md) for gain scaling and lifecycle.

## Persistence boundaries

| Data | Storage |
| --- | --- |
| Three manual save slots | `factorinode.save-slots.v1` |
| Autosave | `factorinode.temporary-save.v1` |
| Shortcut assignments, geometry and attachments | Dedicated `factorinode.shortcut-*` keys |
| Node Map layout | `factorinode.node-map-layout.v1` |
| Unapplied mod draft | `nodefactory.mod-draft.v1` |

New-game autosave defaults to five minutes. Slot metadata includes name, saved time, game time and sector name. The Save / Load panel handles slot actions and file interchange. Browser storage is local to its origin/profile, so different development ports or the published URL can have separate saves.

Manual save slots are inspected independently. A malformed or unsupported slot is shown as **UNREADABLE**, with Load disabled; healthy siblings remain available. Manual saves and copies read the latest stored array and replace only the chosen entry, preserving untouched JSON values, legacy metadata and unreadable payloads without persisting load-time migrations. Replacing an unreadable slot requires the explicit **Replace unreadable save?** confirmation. It does not repair or recover its old contents.

If the complete manual-slot value is malformed, is not an array, or cannot be read from storage, Save / Load shows **UNAVAILABLE** slots and an error, disables manual saves/copies and offers **Retry**. Both persistence writers independently reject the operation before writing, including if storage became unreadable after opening the panel. The panel also reports failed manual writes. [Slot integrity regressions](../../src/persistence/saves.test.ts) cover throwing/unsupported payloads, ordinary saves, copies, raw sibling preservation, fresh reads and blocked writes; [panel checks](../../src/ui/panels/SavePanel.test.tsx) cover the visible status and disabled actions.

Automatic autosave serialization and storage writes are guarded. A failed write leaves the previous autosave intact and simulation continues. A persistent **Autosave failed** alert offers **Retry** and **Export Save**, without a dismissal timer or close action. Retry writes the current factory even while paused; ordinary automatic retries retain the configured active-play interval rather than retrying every frame. Only a successful autosave clears the failure. This runtime status survives undo and factory replacement, is not serialized, and is not created by autosave-disabled practice engines. Separate shortcut, map-layout and mod-draft preference writes are outside this protection.

Save / Load caches its parsed autosave for the mounted panel, refreshing after successful same-window writes, matching cross-tab storage/clear events, window focus and explicit refresh/Retry. Opening always reads current storage; the observer setup rechecks for writes between render and subscription. Ordinary simulation renders and name edits do not reload it, and autosave refresh leaves edited manual names intact. Failed writes retain the previous snapshot; blocked or malformed storage is handled by the existing reader on the next refresh. Observer errors cannot make a completed persistence write appear failed. Manual writes still read the latest raw slot collection independently of this preview cache. See [invalidation coverage](../../src/ui/interfaceSnapshots.test.tsx).

**Export Save** downloads the current factory as a JSON file without using browser storage. The download request does not imply that autosave recovered and does not clear its warning. **Import Save** in Save / Load reads an exported wrapper or supported raw factory snapshot, normalizes it through the existing compatibility loader and asks **Load imported save?** before replacing the current factory. Cancellation and invalid files retain the current factory. Import does not overwrite stored slots or prove storage has recovered. The export/import flow works while browser storage is unavailable. See [autosave writer](../../src/persistence/autosave.ts), [engine recovery tests](../../src/simulation/engine.autosave.test.ts), [portable save tests](../../src/persistence/saveFiles.test.ts), [download tests](../../src/ui/saveFile.test.ts) and [warning presentation](../../src/ui/components/AutosaveWarning.test.tsx).

An applied mod is embedded in game state and restored with the save. The editor draft remains separate unless explicitly loaded from the active mod. Templates and Control Groups live with game state; shortcut and map-layout browser preferences have their own persistence.

The optional hasProducedWithRefiner flag records a completed Refiner batch with positive item output and survives normal save/load even after the producer is removed. Missing flags remain unset; old produced totals and inventory are not treated as proof of machine provenance. Existing completed research IDs remain intact. This remains available to compatible catalogs; Splitter and Merger now use the saved produced['simple-core'] count instead. Their earlier completions remain valid even without that count. The retired simpleCore research ID remains readable while the recipe itself requires no completion marker. New research states carry endgameUnlockVersion: 1: finalCore (Complex upgrade) grants the half recipes and four corner markers; complexCore (Shiny upgrade) alone does not. On loading a state without that marker, prior complexCore or cornerComponents completion sets legacyHalfRecipesUnlocked and legacyCornerLocationsRevealed to true, preserving earned access. An older unlocked/visited corner preserves all-corner knowledge only. These independent optional flags survive save/load; unsupported version values or non-true explicit flags are rejected. No finalCore completion or payment is granted. The migration also retains these old permissions for applied-mod saves without adopting character progression; a custom recipe prerequisite is never bypassed. Retain historical cornerComponents completion records and promote them to complexCore access on normalization, preserving already-earned recipes without a live retired project. Pre-project Final Core migration still uses the historical cornerComponents gate so Shiny upgrade alone never grants the paid Complex upgrade. Revealing locations does not mark sectors visited or unlocked.

The saved research.queue stores up to four ordered projects and research.paused freezes only research processing. Unmodded migration initializes missing fields to an enabled queue, adopting a saved ordinary selection as its head while keeping bot priority outside the queue. Valid existing queue order, selected work, paid contribution bags, buffers and partial Center cycles persist. Reconciliation removes invalid/duplicate/completed/capped entries and limits the queue to four. Disabling a priority upgrade after reload returns to the saved queue while retaining explicit pause. [Queue coverage](../../src/simulation/researchQueue.test.ts) and [actual slot/replacement coverage](../../src/ui/UpgradesIntegration.test.tsx) exercise these rules.

Unmodded new, loaded and replaced factories use mapResearchMode: points. Existing destination quotes keep their exact bill/completion index and active or parked payments while releasing only the destination. Completion banks one point for later Map selection, without opening/visiting a sector. Existing points and map flags stay intact. Active bills remain quoted until completion; the next purchase uses the point schedule. Applied-mod factories are not automatically converted and retain their existing saved rule marker. Unsupported marker values are rejected. [Map conversion coverage](../../previews/status-page/mapPoints.test.ts) checks the retained bill and later spending.

The optional researchHintHistory stores assignmentAcknowledged and ordered unlocked hint title/detail copies for Upgrades. Suggestive headings transform display only; canonical stored keys and normal eligibility remain authoritative. Optional actions re-resolve live eligibility, so stale earned copy cannot expose future research or a locked lesson. Practice return context (hint key, research view/search/completed selection and scroll) is temporary UI state, not a saved unlock or new schema field. Slots, copies, autosaves and file-shaped JSON retain each factory's history. The game's factory observer records current candidates on engine publications even with the modal closed; the thought bubble uses the same record. Normalization drops malformed entries, de-duplicates titles and bounds loaded history to 256 copies without rejecting the factory. Old saves seed current candidates only; Wood/Kiln progress suppresses the introduction. For saved new-world rules, the known obsolete Dwarven Tribute title/detail pair becomes Dwarven Mythril before history merging, even when the discovery is complete. This changes the learned copy without revealing another hint or modifying legacy/custom text. Undo retains learned clues while replacing factories uses their own records. See [history coverage](../../previews/status-page/hintHistory.test.ts) and [integrated slot checks](../../src/ui/UpgradesIntegration.test.tsx).

The optional devTutorialPromptsSuppressed marker keeps automatic tutorial invitations and Dwarven discovery notices quiet in a Dev-used factory. It survives normal save channels and undo, while a new factory starts without it. Older explicit dev research/map flags or existing Dev Sources also suppress automatic notices without fabricating tutorialPromptsSeen entries. Manual lesson availability is unchanged.

## Saved world rules

Landmark eligibility uses independent saved fields, not worldRulesVersion. New standard 11×11 campaigns opt into the implemented layout; missing/zero landmark versions never opt in on load, import, re-save or later exploration. Training retains authored layouts, while larger-world Landmark support and count scaling remain deferred. See [saved Landmarks](#saved-landmarks) and [size-change/mod compatibility](landmarks.md#relocation-and-compatibility) for the authoritative fields and early new-game exceptions.

Only new-game creation selects worldRulesVersion 2. Imports and loads without a marker normalize to version 1; explicit versions survive slot saves, copied slots, autosaves, exports, re-saves, undo and mod activation/removal. Unsupported world-rule versions are rejected rather than silently converted. Never infer a ruleset from the load date or explored-map count.

Version 2 enables guarded camp deposits, revised Deep Hole generation/completion and Lake access/capacity/relocation. Version 1 keeps Tribute and legacy obstruction behavior, including on unexplored maps generated later. New fields preserve guarded owner/lock and regeneration credit, generated/depletion hole origin, and completed grey terrain outside the active node graph. World generation selects the versioned algorithm from the saved marker and seed. Guarded-camp placement corrections apply to newly generated maps; loading a saved map preserves its node positions and cables. The camp’s reverse reserve link is rebuilt from guardedCampId. Default Stone Deposit titles become Stone on load and in templates without changing IDs, quantities or custom names.

The developer full-map reveal stores normal visited flags on every map, alongside its existing dev survey marker. Save/load preserves the explored appearance. Older dev saves with only the survey marker are not silently migrated; the enabled developer action can mark their maps visited on demand. Undo metadata for that command is transient and not serialized; it restores the earlier visit/discovery snapshot.

## Saved landmarks

New standard 11×11 campaigns save landmarkVersion 1 and seventeen initial landmark-sector snapshots in landmarkLayout. Missing/zero versions never opt in, including future unexplored sectors. Loading preserves assigned type, family, source, position and stocks. Instantiated sectors, later player moves and ordinary expansion remain authoritative. Training and larger-world selection omit this layout; custom world-spawn mods retain normal natural generation and place the assigned device among those contents.

Landmark node properties retain three independent Tri Extractor buffers, mixed Core input/output queues, the Unknown Device active Core and progress, and any finished Doubler batch awaiting output space. Cable cargo retains its source outlet for refunds. Normalization rejects unsupported versions and malformed allocations, families, Core identities or branch-buffer data. It does not generate replacement landmarks or reroll chance results. See [Landmarks](landmarks.md) and [headless coverage](../../src/simulation/landmarks.test.ts).

## Saved ground terrain

Ground terrain has a separate optional mapTerrainVersion (0 or 1) and authoritative mapTerrains coordinate-to-type record. Only new-game creation opts into version one. Missing/zero versions retain legacy generation and plain art on every map, including unexplored maps; neither worldRulesVersion 2 nor borderObstructionVersion 1 implies opt-in. Loading never reapplies reserve factors, generates missing assignments or resizes the layout. The rule version fixes the 1.5× placement weight and nine fixed sites; the saved endgame corner order retains encounter identity.

Slots, autosaves, copy, file interchange and undo preserve the complete assignment and adjusted node stocks/caps. Imports reject unsupported versions, incomplete/out-of-bounds layouts, unknown types, incorrect totals or invalid Home/corner/first-diagonal sites. An allowed early grid-size change rebuilds a version-one layout from seed and saved corner order; old worlds stay version zero. Training explicitly opts out. Tests: [terrain integration and compatibility](../../src/simulation/mapTerrain.test.ts).

Deep Holes no longer restrict exploration or purchases of adjacent maps under either world-rule version. This requires no saved marker migration: preserve hole origins, positions, stock, filling progress and completed ground, along with destination quotes and paid contributions. Existing quotes can resume without filling neighboring holes.

## Saved border layouts

Border terrain has an independent `borderObstructionVersion`. New games select version one and store the seeded shared-edge list in `borderObstructions`. Missing or zero versions normalize to an empty version-zero list; later discovery never retrofits terrain into an old world. Reload, imports, undo and mod activation preserve both layout and crossing research. Unsupported versions, malformed/duplicate/nonadjacent edges, right angles, protected-route violations and saved Roads lacking their terrain permission are rejected without deleting cargo or wiring. A permitted larger grid chosen before the first non-Home sector regenerates only a version-one border list at the new size; legacy worlds stay clear. Artwork clearance is a placement correction for subsequently generated sectors in border-version-one worlds. Already saved resource/obstruction positions and wiring are not moved on load, so older generated sectors can retain contact with a border. No new save marker or retrofit is introduced.

## Undo and recovery

The engine retains up to fifty state checkpoints for recorded commands such as placement, movement, deletion or wiring. Undo is not a continuously recorded simulation replay. Long-term recovery should use a saved slot or exported save rather than assuming every production event has an undo entry.

Checkpoints use complete structured clones in memory, evicting the oldest entry above fifty. Undo consumes a retained state rather than cloning the entire state again; its reconciliation and publication still do work. Factory replacement clears the command history. The history is not included in serialized saves, so fifty checkpoints increase retained memory without multiplying the stored autosave by fifty.

The stateless [lifecycle operations](../../src/simulation/stateLifecycle.ts) share only collection initialization between construction/replacement and learned-knowledge retention during Undo. The engine retains the distinct [lifecycle sequences](architecture-and-simulation.md#state-and-mutation): replacement is a full normalization path, Undo restores a command snapshot, and mod application validates and reconciles in its own order. Undo retains learned hints, tutorial suppression, tutorial invitations already seen and depletion notices; ordinary Undo also retains encounters/visited maps, while undoing developer map reveal restores its earlier discovery/visit snapshot. Autosave failure remains outside snapshots. This organization adds no save format or new reset/migration behavior. [Boundary regressions](../../src/simulation/stateLifecycle.test.ts) and [verification](../../outputs/ui-lifecycle-refactor/README.md) retain evidence and limits.

Manual slots share one serialized array: saving one entry writes the collection and normalizes the returned slot views, while preserving raw untouched sibling values. Autosave writes the current state to its own key. Browser quota applies to the origin's storage, including other keys; JSON file bytes, string code units, retained heap and renderer memory are different measurements. The adopted review outcome retains fifty checkpoints and defers a fixed byte budget or alternative undo representation. Revisit if slower-device testing or larger current factories demonstrate a problem. The [bounded undo/save profile](../../outputs/undo-save-profile/README.md) records measured retention, save timings and native storage-failure recovery on declared factory copies; it does not establish a universal supported factory size.

## Migration policy

The revised [map-filter survey proposal](../master-plan/04-world-and-encounters.md#map-filter-research-proposal) retains existing/new unmodded save scope but replaces automatic coverage with separately paid survey research (NODE-0785). Completed character upgrades establish eligibility only; do not synthesize paid survey completions from them. Retain manual discoveries and saved world contents/versions without adding missing Landmarks or border terrain. The author test page exercises isolated survey payments and snapshot retention. Its later combined Exploration/Road fixture retains a Road alias after Exploration (NODE-0791); production adoption still needs a rule for preserving already-paid separate Road contributions. Main-game migration/integration remain future work. Applied-mod Upgrades deferral below is unchanged.

Area Expansion grows equally on all sides at research completion (also when Dev grants missing expansions) and saves the resulting positions/cameras normally. Preserved built/visited layouts receive one rigid coordinate-frame translation, paired with the opposite screen-space camera offset; their field-center positions, visible geometry, internal cable curves and zoom stay fixed. Roads reanchor separately and only their attached vehicle curves change. Completed-hole ground and archived nodes follow their layout frame. Eligible unvisited natural contents spread around the enlarged field center without rerolling contents, recalculating reserves or converting terrain rules. Loading a snapshot repeats neither centering nor redistribution and does not retroactively recenter previously expanded saves. Saved modern corner footprints on discovered/built maps remain fixed through travel/reload; guarded legacy-corner layout migration is separate. Newly generated maps use expanded resource-placement dimensions. No extra saved layout-version marker is required; Road border repair remains a separate load-time rule.

Road border alignment is derived from the completed Area Expansion levels and shared field dimensions during engine initialization. Existing reciprocal pairs stranded at an older border are repositioned on both maps without changing IDs, direction, cable records or vehicle stock. This is a layout repair without a new serialized version or terrain/resource migration. Unavailable or conflicting Road references are left unchanged.

Applied-mod Upgrades support is deliberately deferred. Factories with an applied package keep the existing Research screen and base/mod catalog, without automatic character/map conversion. No mod-price conversion policy has been selected. Removing the package adopts the ordinary unmodded Upgrades rules while retaining earned IDs/payments. Existing mod package persistence remains supported. See [mod scope](mods.md#content-and-rules).

[migrateUpgrades](../../src/simulation/upgradesMigration.ts) runs for unmodded save normalization, engine construction/replacement and return from a modded catalog. Existing Core migration runs first. The highest completed Core recipe project implies its preceding character upgrades; missing earlier milestones are filled without charging again. basicCore maps to Simple character completion, through finalCore mapping to Complex. Historical simpleCore alone and victory do not grant the new Final character upgrade; an explicitly saved finalBotUpgrade remains complete. No separate derived-tier field is stored. Reapplying migration has no further effect and the loader copies its input before normalization.

The integrated screen and migration preserve active/parked contributions, selection, queue, explicit pauses, inventory and partial lab progress. Actual Save / Load slots are covered by [integration tests](../../src/ui/UpgradesIntegration.test.tsx); the author study retains Test saved progress and Test saved map purchase for isolated compatibility examples. Normal game loads now adopt these reviewed unmodded rules. Existing campaign slots were not overwritten during browser verification; browser QA used a separate local origin and its own named test slot.

When a catalog change adds prerequisites to active research, selection reconciliation retains its already-paid Cores under the project ID before clearing the unavailable selection. Connector Mirroring now requires Complex Core research and adds Shiny/Complex inputs to its bill; old completed unlocks remain valid and unfinished lower-tier payments are not charged again.

Original version-one saves and earlier reconstruction payloads normalize into current state. Keep serialized IDs, schema fields and browser keys stable unless a deliberate migration handles them. **Complex Core** retains `command-core`; **Mythril** retains legacy `mithril` substrings in several recipe/item/research IDs. Dwarven settlements retain the `lizardSettlement` field and related module names.

Power equipment, cables, energy and affected in-flight cargo are archived under deferred infrastructure rather than simulated. Retired node aliases, old waste nodes, former recipe layouts and efficiency ranks have targeted migrations. Already-paid batches and cargo must not disappear when changing defaults. Existing reserves, overfilled buffers and legacy layouts can differ from newly generated content.

When changing a recipe, socket or capacity, inspect input/output stock, queues, committed batches, connections, in-flight transfers and templates. A display-name change should not become an item-ID change.
